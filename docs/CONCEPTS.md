# DocSpace 개념 노트

> AI 도움으로 개발하면서도 "왜 이렇게 동작하는가"를 이해하기 위한 학습 노트.
> 한 주제씩 점진적으로 채워간다.

## 1편: 프로젝트 구조

### 1.1 폴더 구조 한눈에

```
myConfluence/
├── apps/
│   ├── web/      ← 사용자가 보는 화면 (Next.js)
│   └── api/      ← 데이터를 처리하는 서버 (NestJS)
├── docs/         ← 문서 (README, DEPLOY, CYCLES, CONCEPTS 등)
├── package.json  ← 프로젝트 정보 + 의존성 목록
├── docker-compose.yml  ← Docker 컨테이너 설정
└── 기타 설정 파일들
```

코드가 두 폴더로 나뉘어 있다 — `apps/web/` 과 `apps/api/`. 각자 자기만의 코드를 가진다.

### 1.2 왜 둘로 나뉘었나? — 식당 비유

**식당 = 우리 프로젝트.** 식당에는 두 가지 다른 일이 일어난다:

- **홀** (손님이 보는 곳) — 메뉴, 테이블, 직원이 손님 맞이
- **주방** (손님이 못 보는 곳) — 재료 보관, 조리, 설거지

손님(브라우저 사용자)은 홀만 본다. 주방에서 무슨 일이 일어나는지 직접 알 수 없다. 손님이 "스파게티 주세요"라고 종업원에게 말하면 종업원이 주방에 주문 넣고, 주방이 만들어서 종업원이 가져다 준다.

우리 프로젝트도:

- **`apps/web/`** = 홀 — 사용자가 보는 화면 (페이지 목록, 편집기, 사이드바)
- **`apps/api/`** = 주방 — 데이터를 처리하는 서버 (회원가입, 페이지 저장, 검색)

### 1.3 왜 합치지 않나? — 이유 셋

1. **서로 다른 일이라서 다른 도구를 쓴다**
   - 홀(UI)은 사용자 경험에 강한 도구 (Next.js, React)
   - 주방(서버)은 데이터/로직 처리에 강한 도구 (NestJS)

2. **사용자에게 보여줄 코드와 숨겨야 할 코드가 다르다**
   - 홀 코드는 브라우저로 다 보냄 → 사용자가 다 볼 수 있음
   - 주방 코드는 서버에만 있음 → 사용자가 못 봄
   - 비밀번호 검증, DB 비밀번호 같은 건 무조건 주방에

3. **나중에 따로 배포하거나 확장 가능**
   - 사용자가 늘면 주방을 여러 개 띄우고 싶을 때 홀은 그대로 두고 주방만 늘릴 수 있음

### 1.4 홀과 주방은 어떻게 대화? — HTTP

```
[브라우저 사용자가 "회원가입" 버튼 누름]
   ↓
[apps/web (홀)] "주방, 새 사용자 만들어줘. 정보는 이거"
   ↓ HTTP 요청 POST /api/auth/signup
[apps/api (주방)] "OK, DB에 저장하고 토큰 발급할게"
   ↓ HTTP 응답
[apps/web (홀)] "OK 받았다, 홈 화면 보여주자"
```

이 두 앱이 서로 어디로 통신하는지(주소 + 포트)가 셋업 시 중요해진다.
예: `apps/web` 의 `next.config.mjs` 가 "주방은 `localhost:3001` 에 있어"라고 알려주면, 그 포트에 NestJS가 떠 있어야 동작한다. Cycle 40 의 PORT 불일치 버그가 정확히 이 부분 때문이었다.

## 2편: 모노레포와 npm workspaces

### 2.1 모노레포가 뭔가

**모노레포 (monorepo) = 여러 프로젝트를 한 폴더(저장소)에 같이 두는 것**

- mono = 하나
- repo = repository (저장소) 의 줄임말

우리 케이스:
- **하나의 GitHub 저장소** (`ldh845/myConfluence`)
- 그 안에 **두 개의 앱** (`apps/web`, `apps/api`)
- 두 앱은 다른 도구를 쓰고 독립적으로 동작
- 하지만 같이 git 으로 관리되고 같이 commit 된다

비유: 한 건물에 두 가게 (식당 + 카페). 건물 주소(저장소)는 하나, 가게는 두 개. 각 가게는 독립적이지만 건물 관리(임대, 청소)는 같이.

### 2.2 모노레포의 대안 — 폴리레포

여러 저장소로 나누는 방식도 가능하다:
- 저장소 1: `ldh845/docspace-web` (홀 코드만)
- 저장소 2: `ldh845/docspace-api` (주방 코드만)

우리는 안 했다. 이유:

1. **같이 변하는 일이 많음** — 새 기능 만들면 보통 web + api 동시 수정. 두 저장소면 따로 commit / push. 모노레포면 한 commit으로 끝
2. **개발 환경 통일** — 한 폴더만 clone 받으면 둘 다 받아진다
3. **버전 동기화 쉬움** — 어느 시점의 web과 api가 짝을 이루는지 자동으로 정해진다

POC 규모에선 모노레포가 거의 항상 편하다.

### 2.3 npm workspaces 가 뭔가

먼저 **npm** 자체를 짧게:
- npm = Node.js의 패키지(라이브러리) 관리 도구
- `npm install` 하면 필요한 라이브러리를 자동으로 받아 `node_modules/` 폴더에 저장
- `package.json` = 어떤 라이브러리가 필요한지 적힌 목록

**npm workspaces** = npm 이 모노레포를 알아주게 만드는 기능

우리 루트 `package.json` 안에 다음이 있다:

```json
{
  "workspaces": ["apps/*"]
}
```

이 한 줄이 npm에게 말한다:
> "이 프로젝트는 `apps/` 폴더 아래에 여러 하위 프로젝트가 있어. 알아서 잘 처리해줘."

### 2.4 workspaces 가 있으면 뭐가 달라지나

**없으면 (각 앱 따로 설치):**
```bash
cd apps/web
npm install        # apps/web/node_modules 만들어짐

cd ../api
npm install        # apps/api/node_modules 만들어짐
```
→ 두 번 명령. 같은 라이브러리도 두 폴더에 중복 다운로드.

**있으면 (한 번에 다 설치):**
```bash
cd myConfluence  # = 루트
npm install        # 자동으로 apps/web + apps/api 둘 다 처리
```
→ 한 번 명령. 같은 라이브러리는 루트 `node_modules` 에 한 번만 (디스크 절약).

### 2.5 `npm run dev:all` 의 비밀

루트 `package.json` 안에 다음이 있다:

```json
{
  "scripts": {
    "dev:all": "concurrently -n web,api -c blue,magenta \"npm:dev\" \"npm:dev:api\""
  }
}
```

`dev:all` 명령이 하는 일:
- `concurrently` = 여러 명령을 동시에 실행하는 도구 (npm 라이브러리)
- `npm:dev` = `apps/web` 의 dev 스크립트 (Next.js 띄움)
- `npm:dev:api` = `apps/api` 의 dev 스크립트 (NestJS 띄움)
- 둘을 동시에 실행하면서 출력 앞에 `[web]` / `[api]` 라벨 붙임

그래서 한 터미널에서 두 앱이 동시에 동작한다.

## 3편: 언어 vs 프레임워크 vs 라이브러리

### 3.1 비유로 구분

| 개념 | 비유 |
|------|------|
| **언어** (Language) | 한국어 / 영어 (말 자체) |
| **런타임** (Runtime) | 그 언어를 말할 수 있는 환경 |
| **프레임워크** (Framework) | 정해진 레시피 + 주방 구조 — 정해진 흐름대로 요리해야 함 |
| **라이브러리** (Library) | 미리 만들어둔 양념 / 도구 세트 — 필요할 때만 꺼내 씀 |

코드 관점에서 가장 큰 차이:
- **프레임워크는 너의 코드를 호출한다** ("정해진 시점에 너 코드 실행할게")
- **라이브러리는 너가 호출한다** ("필요할 때 우리 함수 부르면 돼")

### 3.2 우리 프로젝트의 층

#### 진짜 언어 (가장 아래)

- **JavaScript (JS)** — 브라우저와 서버 양쪽에서 도는 언어
- **TypeScript (TS)** — JavaScript 에 "타입"이라는 안전장치를 추가한 언어. 빌드되면 JavaScript 로 변환됨. 우리 프로젝트는 거의 다 TypeScript 로 작성.

→ `.ts` 파일 안에 있는 코드가 TypeScript. 빌드 시점에 JavaScript 로 변환돼 실행됨.

#### 런타임

- **Node.js** — JavaScript 를 브라우저 밖(서버, 명령줄)에서 실행할 수 있게 해주는 환경
- **브라우저** — JavaScript 를 클라이언트 쪽에서 실행

`node` 명령으로 서버 코드 돌리는 게 Node.js. 브라우저는 그냥 브라우저.

#### 프레임워크 / 라이브러리

**React** — UI 라이브러리
- 만든 곳: Meta (예전 Facebook)
- 하는 일: 화면(UI)을 컴포넌트 단위로 조립하게 해줌
- 레벨: 라이브러리에 가까움 (단, 모듈 묶음이 커서 흔히 프레임워크로 부르기도)
- 특징: "UI 컴포넌트 그리기"만 한다. 페이지 이동, 데이터 가져오기 등은 다른 도구 필요.

```tsx
// React 컴포넌트 예시
function Button() {
  return <button>클릭</button>;
}
```

**Next.js** — React 를 감싼 풀스택 프레임워크
- 만든 곳: Vercel
- 하는 일: React에 빠진 부분(라우팅, SSR, 빌드, 환경설정 등)을 다 채워줌
- 레벨: 프레임워크 (정해진 폴더 구조 + 정해진 흐름)
- 특징: "이 폴더에 페이지 만들면 자동으로 라우팅됨" 같은 규칙 강제

`apps/web/` 가 Next.js 프로젝트. 예: `apps/web/app/login/page.tsx` 만들면 `/login` 주소로 자동 매핑.

**NestJS** — 서버 백엔드 프레임워크
- 만든 곳: Kamil Mysliwiec + 커뮤니티
- 하는 일: 서버 API를 모듈 단위로 깔끔하게 구조화. Controller / Service / Module 같은 패턴 강제.
- 레벨: 프레임워크 (정해진 패턴 강제)
- 특징: TypeScript 친화적. Angular 와 비슷한 디자인.

`apps/api/` 가 NestJS 프로젝트. 예: `apps/api/src/auth/auth.controller.ts` 가 인증 API 담당.

### 3.3 발음

- **Next.js** = "넥스트 닷 제이에스" 또는 그냥 "넥스트"
- **NestJS** = "네스트 제이에스" 또는 그냥 "네스트"
- **React** = "리액트"

영문으로:
- **Nex**t.js (홀 / 프론트엔드)
- **Nes**tJS (주방 / 백엔드)

이름이 너무 비슷하다 — t/s 만 다름. 처음 듣는 사람은 헷갈린다. 외울 때:
- 브라우저에서 다음 페이지(Next)로 넘어가니까 → Next.js
- 백엔드는 코드를 둥지(Nest)처럼 모듈로 감싸니까 → NestJS

이름이 비슷한 건 우연이다. 두 도구는 만든 회사도 다르다.

### 3.4 정리 표

| 이름 | 종류 | 우리 프로젝트에서 위치 |
|------|------|----------------------|
| JavaScript / TypeScript | 언어 | 모든 코드의 바탕 |
| Node.js | 런타임 | 서버 실행 환경 |
| React | 라이브러리 (UI) | `apps/web/` 안에서 화면 그리기 |
| Next.js | 프레임워크 (풀스택 React) | `apps/web/` 의 전체 구조 |
| NestJS | 프레임워크 (서버) | `apps/api/` 의 전체 구조 |

### 3.5 의외의 사실 — Next.js 와 React 의 관계

Next.js 는 **React 를 안에 품고 있다.** Next.js 가 자기 일을 하려면 React 가 무조건 필요해서 같이 설치된다. Next.js 만 깔면 React 자동 따라옴.

NestJS 와 React 는 무관. NestJS 는 서버라서 화면 라이브러리가 필요 없다.
